Header-only C++17 · CMake · MIT

Pipelined receiver chains without the threading code

pipeline turns a chain of processing blocks (demodulator, decoder, data link, …) into a multi-threaded pipeline. Every stage runs on its own thread, bounded queues match the rates automatically, slow stages can run on several threads while keeping the output order, and every block exposes controls and monitors that a user interface can read and change while the chain runs.

The whole receiver above, including its UI hooks, is this much code:

#include <pipeline/pipeline.hpp>
using namespace pipeline;

Pipeline rx("receiver");
auto iq   = rx.source<AdcSource>("adc", "/dev/sdr0");    // ctor args follow the name
auto soft = rx.add<Demodulator>("demod", iq);
auto bits = rx.add<Decoder>("decoder", soft, opts().autoscale(1, 8));  // 1..8 threads
auto pkts = rx.add<DataLink>("datalink", bits);
rx.sink<AppSink>("app", pkts);

rx.start();
rx.setControl("decoder.iterations", 12);  // from your UI, any thread
std::string json = rx.snapshotJson();     // rates, queues, workers, parameters
rx.stop();                                // drain, flush, join

01Add it to your project

The library is header-only. Its CMake target pipeline::pipeline adds the include path, requires C++17 and links the platform thread library. Pick whichever of the three ways fits your build:

Copy or add the repository as a git submodule, for example under third_party/pipeline.

# your project's CMakeLists.txt
add_subdirectory(third_party/pipeline)    # tests and examples are skipped automatically

add_executable(my_receiver main.cpp)
target_link_libraries(my_receiver PRIVATE pipeline::pipeline)

CMake downloads the library at configure time.

include(FetchContent)
FetchContent_Declare(pipeline
  GIT_REPOSITORY https://github.com/mohamadmovahed/pipeline.git
  GIT_TAG        main)            # pin a tag or commit for reproducible builds
FetchContent_MakeAvailable(pipeline)

target_link_libraries(my_receiver PRIVATE pipeline::pipeline)

Install once, then use it like any other package.

# once, from the pipeline checkout
cmake -S . -B build -DPIPELINE_BUILD_TESTS=OFF -DPIPELINE_BUILD_EXAMPLES=OFF
cmake --install build --prefix /opt/pipeline
# in your project (configure with -DCMAKE_PREFIX_PATH=/opt/pipeline)
find_package(pipeline 1.0 REQUIRED)
target_link_libraries(my_receiver PRIVATE pipeline::pipeline)

To build and try the repository itself (tests and both examples):

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure
./build/examples/receiver_chain --seconds 9

Requirements. A C++17 compiler (GCC 9+, Clang 10+, MSVC 2019+) and CMake 3.16+. No other dependencies.

02Concepts

Block<In, Out>
Your processing code. process() receives one input and may emit zero, one or many outputs.
Source<Out>
The start of the chain (ADC, file, socket). produce() returns false at end of stream.
Sink<In>
The end of the chain (application, file, network).
Emitter<T>
Where a block puts its outputs: out.emit(std::move(x)).
Stage
A block placed in a pipeline: its input queue, one or more worker threads (each with its own block instance), statistics and parameters.
Port<T>
The typed output of a stage. You pass it to the next stage; mismatched types fail at compile time.
Control<T>
A parameter the UI writes and the block reads (gain, iterations, bandwidth).
Monitor<T>
A value the block publishes for the UI (SNR, CRC failures, lock state).
Pipeline
Owns the stages, starts and stops threads, runs the autoscaler and produces snapshots for the UI.

Items move between stages by std::move; a std::vector of samples is never copied by the library. Every item carries a sequence number, which is what lets a parallel stage put its results back in order.

03Write a block

First define the data that flows between blocks. Any movable type works; carrying a frame counter is useful for debugging.

struct IqBlock   { std::uint64_t frame; std::vector<std::complex<float>> samples; };
struct SoftFrame { std::uint64_t frame; std::vector<float> llr; };

A block derives from pipeline::Block<In, Out> and overrides process(). Controls and monitors are declared as member references, initialised by control<T>() and monitor<T>():

class Demodulator : public pipeline::Block<IqBlock, SoftFrame> {
 public:
  void process(IqBlock&& in, pipeline::Emitter<SoftFrame>& out) override {
    SoftFrame f{in.frame, {}};
    f.llr.reserve(in.samples.size());
    const float g = static_cast<float>(gain_.get());
    for (const auto& s : in.samples) f.llr.push_back(g * s.real());

    snr_ = estimateSnrDb(in.samples);   // publish a value to the UI
    out.emit(std::move(f));             // one output for this input
  }

 private:
  pipeline::Control<double>& gain_ =
      control<double>("llr_gain", 1.0, "extra LLR scaling", {0.01, 100.0});
  pipeline::Monitor<double>& snr_ =
      monitor<double>("snr_est", "estimated Es/N0", pipeline::Aggregate::Mean, "dB");
};

No locks needed inside a block. When a stage runs on several threads, each thread gets its own instance of the block. Members such as filter states, buffers and random generators are therefore private to one thread. Control changes from the UI are applied by the block's own thread between two calls to process(), so a value never changes in the middle of an item.

Sources and sinks look the same:

class AdcSource : public pipeline::Source<IqBlock> {
 public:
  explicit AdcSource(std::string device) : dev_(std::move(device)) {}
  bool produce(pipeline::Emitter<IqBlock>& out) override {
    IqBlock b{frame_++, dev_.read(4096)};        // blocks until the hardware has data
    out.emit(std::move(b));
    return !stopRequested();                    // false = end of stream
  }
 private:
  SdrDevice dev_;
  std::uint64_t frame_ = 0;
};

class AppSink : public pipeline::Sink<NetPacket> {
 public:
  void consume(NetPacket&& p) override { socket_.send(p.payload); ++packets_; }
 private:
  UdpSocket socket_{"10.0.0.2", 5000};
  pipeline::Monitor<std::int64_t>& packets_ =
      monitor<std::int64_t>("packets", "packets delivered", pipeline::Aggregate::Sum);
};

The hooks onStart() and onStop() run on the worker thread before the first and after the last item. Use them for thread-affine setup such as opening a device or allocating a GPU stream.

04Assemble the chain

using namespace pipeline;

Pipeline rx("receiver");

Port<IqBlock>      iq   = rx.source<AdcSource>("adc", std::string("/dev/sdr0"));
Port<SoftFrame>    soft = rx.add<Demodulator>("demod", iq);
Port<DecodedFrame> bits = rx.add<Decoder>("decoder", soft, opts().autoscale(1, 8).queue(64));
Port<NetPacket>    pkts = rx.add<DataLink>("datalink", bits);
rx.sink<AppSink>("app", pkts);

rx.start();     // one thread per worker + one supervisor thread
// ... the application runs; the UI reads rx.snapshot() and calls rx.setControl(...)
rx.stop();      // sources stop, queued data is processed and flushed, threads joined

Each call returns the Port of the new stage, which you pass to the next call. Stage names must be unique and contain no dot, because controls are addressed as "stage.control". start() checks that every output is connected and throws std::logic_error otherwise.

The opts() builder sets the per-stage options:

OptionDefaultMeaning
.parallel(n)1Run the stage on n worker threads.
.autoscale(min, max)offLet the pipeline choose between min and max workers at run time.
.queue(n)64Capacity of the stage's input queue, in items.
.unordered()orderedParallel results may leave in completion order.
.onError(policy)SkipWhat happens when process() throws. See section 11.
.reorderWindow(n)4×max+4How far ahead of the oldest unfinished item a parallel worker may run.

05Different rates are handled for you

Every stage reads from a bounded queue. When a stage is slower than the one before it, its queue fills up and the producer blocks in push() until there is room again. This is backpressure: the whole chain settles at the speed of its slowest stage, no data is dropped and memory stays bounded. You never write rate-matching code.

A stage's rate is set by how many items it emits per input. Each of these needs nothing more than the right number of emit() calls:

PatternIn : outHow
Demodulator1 : 1Emit once per input.
Packing frames into packets, decimationN : 1Accumulate in a member, emit every N inputs, emit the rest in flush().
Segmentation, channelizer, interpolation1 : NCall emit() N times.
CRC check, squelch1 : 0 or 1Return without emitting to drop the item.
 
class DataLink : public pipeline::Block<DecodedFrame, NetPacket> {
 public:
  void process(DecodedFrame&& in, pipeline::Emitter<NetPacket>& out) override {
    if (!crcOk(in)) { ++crcFail_; return; }          // 0 outputs: frame dropped
    pending_.append(in);
    if (pending_.frames == framesPerPacket_.get()) {  // N inputs -> 1 output
      out.emit(std::move(pending_));
      pending_ = {};
    }
  }
  void flush(pipeline::Emitter<NetPacket>& out) override {   // end of stream
    if (pending_.frames) out.emit(std::move(pending_));
    pending_ = {};
  }
 private:
  pipeline::Control<int>& framesPerPacket_ =
      control<int>("frames_per_packet", 4, "good frames per packet", {1, 64});
  pipeline::Monitor<std::int64_t>& crcFail_ =
      monitor<std::int64_t>("crc_fail", "frames with bad CRC", pipeline::Aggregate::Sum);
  NetPacket pending_;
};
void process(Burst&& in, pipeline::Emitter<Symbol>& out) override {
  for (auto& sym : split(in)) out.emit(std::move(sym));   // 1 input -> many outputs
}

flush() is called once at end of stream (after stop() or when the source ends), so partially filled packets are not lost.

How fast will the chain run?

Throughput is the smallest capacity of any stage, where capacity is workers × items per second per worker. Change the numbers to see where your bottleneck is and how many workers it needs. The defaults match the example receiver: the decoder is about 4× slower than the demodulator.

Stageframes/s per workerworkerscapacity

In the running library you do not have to compute this: the snapshot reports each stage's utilization and the pipeline names the busiest stage in bottleneck.

06Parallel stages

A stage with more than one worker has one block instance per worker, all reading the same input queue. Results go through a reorder buffer keyed by the input's sequence number, so the next stage sees exactly the order it would have seen with one worker.

// fixed: 4 decoder threads, output order preserved
rx.add<Decoder>("decoder", soft, opts().parallel(4));

// automatic: start with 1 thread, grow up to 8 while the decoder is the bottleneck
rx.add<Decoder>("decoder", soft, opts().autoscale(1, 8));

// order not needed downstream: skip the reorder buffer
rx.add<Decoder>("decoder", soft, opts().parallel(4).unordered());

// constructor arguments come after the options; every replica gets a copy
auto code = std::make_shared<const LdpcCode>(LdpcCode::load("wifi_1944_r12.alist"));
rx.add<Decoder>("decoder", soft, opts().autoscale(1, 8), code);

Only parallelise independent items. Running a block on several workers is correct when each input can be processed on its own, such as one codeword per decoder call. A block that carries state from one item to the next (a PLL, an equaliser, an accumulator like the data link above) must stay at one worker, or must be redesigned so that each item contains everything it needs.

The reorder window bounds memory: a worker that finishes far ahead of the oldest item still in progress waits before taking new work. Use .unordered() when the downstream stage does not care about order (for example a sink that writes independent packets); it skips the reorder step.

Constructor arguments passed to add<B>() are copied into every replica. For large read-only data such as code tables, pass a std::shared_ptr<const T> so all replicas share one copy.

07Autoscaling

With opts().autoscale(min, max) the pipeline's supervisor thread checks every stage each monitorPeriod and adds or removes one worker at a time:

DecisionWhen
add workerutilization ≥ scaleUpUtilization and input queue fill ≥ scaleUpQueueFill and workers < max
remove workerutilization ≤ scaleDownUtilization and input queue fill ≤ scaleDownQueueFill and workers > min

Utilization counts only the time spent inside process(). A stage that is waiting on a slow downstream stage has a full input queue but low utilization, so it is not scaled up; only the real bottleneck is. A cooldown between two decisions for the same stage lets the queues settle.

pipeline::PipelineOptions po;
po.monitorPeriod        = std::chrono::milliseconds(250);  // rates, autoscaler and onUpdate period
po.autoscale            = true;
po.scaleUpUtilization   = 0.80;   // add a worker when utilization >= 80 % ...
po.scaleUpQueueFill     = 0.50;   // ... and the input queue is at least half full
po.scaleDownUtilization = 0.30;   // remove one when utilization <= 30 % ...
po.scaleDownQueueFill   = 0.05;   // ... and the input queue is (nearly) empty
po.scaleCooldown        = std::chrono::milliseconds(1000);
pipeline::Pipeline rx("receiver", po);

rx.stage("decoder").setWorkers(6);   // manual override, clamped to [1, maxWorkers]

The example receiver prints this when started with a decoder that is too slow for one thread, then made cheaper from the UI after six seconds:

tdecoder workersdecoder utilizationdecoder queueevent
1 s3/497 %64/64scaling up to catch up the backlog
2 s4/476 %0/64keeping up with 4000 frames/s
6 s4/458 %0/64UI sets decoder.iterations 300 → 60
7 s2/417 %0/64scaling down
8 s1/435 %0/64one worker is enough

Retiring a worker is safe: it finishes its current item, flushes, and its counters (monitors aggregated with Sum) are kept in the stage totals.

08Controls and monitors

Declare parameters as member references. The arguments are the name, the initial value (controls) or the aggregation (monitors), a description, an optional range and an optional unit. The UI gets all of this metadata, so it can build its widgets without any extra configuration.

class ChannelFilter : public pipeline::Block<IqBlock, IqBlock> {
 public:
  ChannelFilter() {
    taps_ = designLowpass(bandwidth_.get());
    // runs on this block's worker thread, between two process() calls
    bandwidth_.onChange([this](const double& bw) { taps_ = designLowpass(bw); });
  }
  void process(IqBlock&& in, pipeline::Emitter<IqBlock>& out) override {
    filter(in.samples, taps_);
    overloads_ += countClipped(in.samples);
    out.emit(std::move(in));
  }
 private:
  pipeline::Control<double>& bandwidth_ =
      control<double>("bandwidth", 200e3, "channel bandwidth", {1e3, 10e6}, "Hz");
  pipeline::Control<bool>& bypass_ = control<bool>("bypass", false, "pass samples through");
  pipeline::Monitor<std::int64_t>& overloads_ =
      monitor<std::int64_t>("overloads", "clipped samples", pipeline::Aggregate::Sum);
  std::vector<float> taps_;
};

Supported types are bool, integer and enum types (shown as int), float and double (shown as double) and std::string.

Thread safety

  • setControl() may be called from any thread. The value is checked against the range immediately and an invalid value throws without changing anything.
  • The new value is applied by the block's worker thread before its next item; onChange callbacks run there too. Inside the block, read controls with get(); no lock is involved.
  • Monitors of arithmetic type are lock-free atomics. Write them with =, += or ++.
  • A control set on a parallel stage is applied to every replica, including replicas the autoscaler starts later.

Monitors of parallel stages

Each replica has its own monitor values. The Aggregate chosen at declaration says how they are combined for the UI:

AggregateUse forExample
SumCountersframes decoded, CRC failures, bytes
Mean (default)EstimatesSNR, EVM, average iterations
Min / MaxWorst or best casepeak level, worst-case latency
FirstValues that are the same in every replicamode, lock state, a status string

Reading and writing from outside

rx.setControl("filter.bandwidth", 125e3);              // typed value
rx.setControl("filter.bypass", true);
rx.setControlFromString("decoder.iterations", "12");   // text from a UI field or a command line
pipeline::Value v = rx.getControl("filter.bandwidth");  // the value the UI should show
pipeline::Value n = rx.getMonitor("filter.overloads");  // aggregated over all replicas

try {
  rx.setControl("filter.bandwidth", 50e6);             // outside {1e3, 10e6}
} catch (const std::out_of_range& e) {
  showError(e.what());                                 // nothing was changed
}

09Connect a user interface

The library has no GUI dependency. It gives you a PipelineSnapshot: plain structs with, for every stage, the worker count, input and output rates, utilization, backpressure, queue fill, error count, and every control (with type, range, unit and description) and monitor. There are two ways to get it.

Poll from the UI thread

snapshot() is thread-safe and cheap enough to call a few times per second.

// Qt example: refresh a table from a timer on the GUI thread
QObject::connect(&timer, &QTimer::timeout, [&] {
  const pipeline::PipelineSnapshot s = rx.snapshot();
  statusBar->showMessage(QString("bottleneck: %1").arg(QString::fromStdString(s.bottleneck)));
  for (int r = 0; r < static_cast<int>(s.stages.size()); ++r) {
    const pipeline::StageSnapshot& st = s.stages[r];
    table->setItem(r, 0, new QTableWidgetItem(QString::fromStdString(st.name)));
    table->setItem(r, 1, new QTableWidgetItem(QString("%1/%2").arg(st.workers).arg(st.maxWorkers)));
    table->setItem(r, 2, new QTableWidgetItem(QString::number(st.inRate, 'f', 0)));
    table->setItem(r, 3, new QTableWidgetItem(QString::number(100 * st.utilization, 'f', 0) + " %"));
    table->setItem(r, 4, new QTableWidgetItem(QString("%1/%2").arg(st.queueSize).arg(st.queueCapacity)));
  }
});
timer.start(250);

// a spin box bound to a control
QObject::connect(snrSpin, qOverload<double>(&QDoubleSpinBox::valueChanged),
                 [&](double v) { rx.setControl("demod.llr_gain", v); });

Push to the UI

// Push model: called on the supervisor thread every monitorPeriod. Register before start().
rx.onUpdate([&](const pipeline::PipelineSnapshot& s) {
  websocket.broadcast(pipeline::toJson(s));     // or copy s and post it to your GUI thread
});

// and the way back, e.g. a message {"path": "decoder.iterations", "value": "12"}
void onMessage(const std::string& path, const std::string& value) {
  rx.setControlFromString(path, value);         // throws std::invalid_argument / std::out_of_range
}

10Wrap existing processing libraries

You do not have to write a class for every step. When the processing already exists as a function in your DSP or FEC library, wrap it in a lambda:

CallCallable signature
rx.sourceFn<Out>(name, f)bool f(Emitter<Out>&)
rx.map(name, port, f, opts)Out f(In&&) — output type is deduced
rx.blockFn<Out>(name, port, f, opts)void f(In&&, Emitter<Out>&)
rx.sinkFn(name, port, f, opts)void f(In&&)
 
// Your existing library, unchanged:
//   std::vector<std::uint8_t> ldpc::decode(const std::vector<float>& llr, int maxIterations);
//   std::vector<IqBlock>       dsp::channelize(const IqBlock& wideband, int channels);

int frame = 0;
auto iq = rx.sourceFn<IqBlock>("file", [frame, f = std::make_shared<IqFile>("capture.cf32")]
                                       (pipeline::Emitter<IqBlock>& out) mutable {
  auto samples = f->read(4096);
  if (samples.empty()) return false;               // end of file = end of stream
  out.emit(IqBlock{static_cast<std::uint64_t>(frame++), std::move(samples)});
  return true;
});

// 1 -> N: one item per channel
auto chans = rx.blockFn<IqBlock>("channelizer", iq, [](IqBlock&& in, pipeline::Emitter<IqBlock>& out) {
  for (auto& ch : dsp::channelize(in, 8)) out.emit(std::move(ch));
});

auto soft = rx.add<Demodulator>("demod", chans);

// 1 -> 1, output type deduced from the lambda; runs on up to 8 threads, order kept
auto bits = rx.map("decoder", soft, [](SoftFrame&& f) {
  return DecodedFrame{f.frame, ldpc::decode(f.llr, 20)};
}, pipeline::opts().autoscale(1, 8));

rx.sinkFn("print", bits, [](DecodedFrame&& d) {
  std::printf("frame %llu: %zu bytes\n", static_cast<unsigned long long>(d.frame), d.bytes.size());
});

The callable is copied once per worker, the same way block constructor arguments are. Lambda stages have no controls or monitors of their own; when a step needs them, turn it into a small class.

11Start, stop and errors

rx.start();

rx.wait();                                        // until the sources end and all data is drained
bool done = rx.waitFor(std::chrono::seconds(5));  // same, with a timeout
rx.stop();                                        // graceful: stop sources, drain, flush, join
rx.abort();                                       // immediate: drop queued data, join

if (rx.state() == pipeline::PipelineState::Aborted)
  std::cerr << "receiver stopped: " << rx.snapshot().error << "\n";
CallWhat happens
stop()Sources stop after their current produce(). Everything already in the queues is processed, every block is flushed, then threads are joined. State becomes Finished.
abort()Queues are cleared and all waits are woken. No flush. State becomes Aborted.
source returns falseEnd of stream; the chain drains and finishes on its own. Use wait().
destructorCalls abort() if the pipeline is still running.

A source that blocks on hardware should check stopRequested() or use a read timeout, so that stop() and abort() return promptly.

Exceptions in blocks

// default: count the error, drop that item, keep going
rx.add<Decoder>("decoder", soft, opts().onError(pipeline::ErrorPolicy::Skip));

// a broken stage aborts the whole pipeline
rx.add<DataLink>("datalink", bits, opts().onError(pipeline::ErrorPolicy::Stop));

With either policy the stage's errors counter and lastError message appear in the snapshot. With Stop, snapshot().error holds "stage: message" of the first fatal error.

12Receivers started on demand

A multichannel receiver often watches a wideband capture and runs a receiver chain only while a channel is active. Two pieces make this simple: a push input, so your own code can feed a running pipeline, and a pipeline pool, which starts receivers by id and stops them without blocking the caller.

Push input: feed a pipeline from your code

input<T>() creates a source stage plus a Feeder<T> handle. The feeder is cheap to copy, thread safe, and stays valid after the pipeline is gone: pushes then simply return false.

Pipeline rx("ch7");
auto [port, feeder] = rx.input<ChannelBlock>("in", 32);   // 32 = input queue size
auto soft = rx.add<Demodulator>("demod", port);
// ... rest of the chain ...
rx.start();

feeder.push(std::move(blk));      // waits while the input is full
feeder.tryPush(std::move(blk));   // never waits; false + counted drop if full
feeder.close();                   // end of burst: drain, flush, finish
CallWhen the input queue is fullUse from
push(x)waits for rooma thread that may slow down (file playback, tests)
tryPush(x)returns false, counts a dropa real-time thread that serves many channels
pushFor(x, timeout)waits up to timeouta compromise between the two

The input stage publishes backlog and dropped monitors. A graceful stop() processes what is still queued in the input before the chain finishes.

Pipeline pool: many receivers that come and go

std::unique_ptr<pipeline::Pipeline> makeReceiver(int channel, pipeline::Feeder<ChannelBlock>& feeder) {
  auto rx = std::make_unique<pipeline::Pipeline>("ch" + std::to_string(channel));
  auto in   = rx->input<ChannelBlock>("in", 32);
  auto soft = rx->add<Demodulator>("demod", in.port);
  auto bits = rx->add<Decoder>("decoder", soft, pipeline::opts().autoscale(1, 4));
  auto pkts = rx->add<DataLink>("datalink", bits);
  rx->sink<Output>("output", pkts);
  feeder = in.feeder;      // hand the input to the caller
  return rx;               // not started: the pool starts it
}
pipeline::PipelinePool pool("receivers");
pool.onFinished([](const std::string& id, const pipeline::PipelineSnapshot& last) {
  log("%s done: %s packets", id.c_str(), toString(last.stage("datalink")->monitors[0].value).c_str());
});

// channel 7 became active
pipeline::Feeder<ChannelBlock> feeder;
pool.start("ch7", makeReceiver(7, feeder));   // builds and starts; returns immediately
feeder.tryPush(std::move(blk));               // feed it from the wideband thread

// channel 7 went quiet
pool.stop("ch7");    // returns at once; drains and flushes in the background
                     // "ch7" can be started again right away

pool.setControl("ch3", "decoder.iterations", 12);   // talk to one receiver
std::string ui = pool.snapshotJson();               // every running receiver, for the UI

pool.stopAll();      // shutdown
pool.waitAll();
  • start(id, pipeline) throws std::logic_error if id is already running.
  • stop(id) and abort(id) never block. A background thread joins finished receivers and calls onFinished with the last snapshot.
  • A receiver that ends by itself (its feeder was closed, or a fatal error) is removed from the pool automatically; its feeder's pushes then return false, which tells the caller to restart it if needed.
  • The id is free again as soon as stop() returns, even while the old receiver is still draining, so a channel that flickers off and on gets a new receiver immediately.

Putting it together: the dispatcher

The front end is an ordinary pipeline (sdr → channelizer → dispatcher). The dispatcher is a sink that detects activity and manages the pool. Detection uses hysteresis so that a receiver is not started and stopped on every noisy block:

class Dispatcher : public pipeline::Sink<ChannelizedBlock> {   // runs on 1 worker: it has per-channel state
 public:
  explicit Dispatcher(pipeline::PipelinePool* pool) : pool_(pool) {}

  void consume(ChannelizedBlock&& in) override {
    for (int c = 0; c < static_cast<int>(in.channel.size()); ++c) {
      ChannelState& st = state_[c];
      st.above = in.powerDb[c] > onDb_.get()  ? st.above + 1 : 0;   // TODO: your detector
      st.below = in.powerDb[c] < offDb_.get() ? st.below + 1 : 0;

      if (!st.running && st.above >= attack_.get()) {               // channel came up
        pool_->start("ch" + std::to_string(c), makeReceiver(c, st.feeder));
        st.running = true;
      }
      if (st.running && st.below >= hang_.get()) {                  // channel went quiet
        pool_->stop("ch" + std::to_string(c));
        st.running = false;
      }
      if (st.running) st.feeder.tryPush(ChannelBlock{c, in.seq, std::move(in.channel[c])});
    }
  }
  void flush() override {                                           // front end stopping
    for (auto& [c, st] : state_) if (st.running) pool_->stop("ch" + std::to_string(c));
  }
  // ... state_ (std::map<int, ChannelState>), pool_, and the controls on_threshold,
  //     off_threshold, attack_blocks, hang_blocks: see examples/multichannel_receiver.cpp
};

Settings for future receivers. Controls set on running receivers do not reach receivers started later. Keep the UI's current values in one place and apply them in makeReceiver() before the pool starts the pipeline. The example's ReceiverDefaults class does this.

The complete template is examples/multichannel_receiver.cpp. It simulates 8 channels that switch on and off, starts and stops one receiver per active channel, prints a dashboard every second and changes receiver settings while running. All DSP steps are stubs marked TODO(dsp).

Threads per receiver. Every pipeline has one thread per worker plus a supervisor thread, so a 5-stage receiver uses at least 6 threads. That is fine for tens of simultaneous channels. For hundreds, give each receiver fewer stages (combine cheap steps into one block) and keep autoscale maxima small.

13Performance tips

  • Make items big enough. Passing one item through a queue costs a few microseconds (measured 2–8 µs per item on a 4-core VM). Pass frames, codewords or blocks of 1k–10k samples, never single samples. A good item takes at least 50–100 µs to process.
  • Move, don't copy. Take the input by In&&, modify it in place where you can and emit(std::move(...)) it.
  • Size queues for jitter, not throughput. Queues absorb bursts; they do not make anything faster. 16–64 items is usually enough. Large queues add latency.
  • Leave a core for the source. A source that reads hardware in real time should not compete with decoder workers; set autoscale(1, cores - 1).
  • Read the snapshot. The stage with utilization near 100 % is your bottleneck. A stage with high backpressure is fast enough and waiting for the next one.
  • Sources look busy. Time a source spends waiting for hardware inside produce() counts as utilization. That is why sources are never reported as the bottleneck.

15Limits and FAQ

Can one output feed two stages?

No. Each output has exactly one consumer, so the graph is a chain. To fan out, consume both paths in one block, or end the chain in a sink that pushes into a second pipeline's source.

Can a source run in parallel?

No. Sources always have one worker, because their order defines the sequence numbers. Make the source cheap (read and forward) and move work into the next stage.

Can I restart a pipeline?

A pipeline runs once. Build a new one to run again; building is cheap. For receivers that start and stop repeatedly, let a PipelinePool do it (section 12).

What happens to a block's state when a worker is retired?

Its flush() is called and its outputs are sent on, then the instance is destroyed. This is one more reason to keep parallel blocks stateless between items.

Which thread calls what?

Each worker thread calls onStart, process/produce/consume, onChange callbacks, flush and onStop for its own block instance. The supervisor thread calls onUpdate. Your UI thread calls snapshot and setControl.
